## Why

Сервисы переведены с `net6.0` на `net8.0`, но граф зависимостей за проектом не поехал. NuGet при
восстановлении выбирает наибольшую папку ассетов, не превышающую таргет: если у пакета есть
`lib/net6.0` и нет `lib/net8.0`, под таргетом `net8.0` он молча отдаёт net6-сборку. Ни ошибки, ни
предупреждения сборки при этом нет.

В результате в приложении на net8 живёт слой библиотек, собранных под net6, net5, netcoreapp2.1 и
netstandard1.x. Он тянет старые API-контракты, лишние пакеты-фасады (`System.Runtime 4.1.0`,
`System.Text.Json 4.7.2`) и мешает выкинуть net6 из таргетов окончательно. Найти этот слой руками
по `project.assets.json` можно, но на 230 пакетов это несколько часов работы, и результат
невозможно передать другому человеку.

Оператору нужно не «список подозрительных пакетов», а ответ на вопрос **что именно обновить в
csproj**: транзитивную версию напрямую не поднять, обновлять надо ту прямую зависимость, которая
её тянет.

Отдельное требование: мультитаргетность ошибкой не считается. Проекты используют условные ссылки
(`Condition="'$(TargetFramework)'=='net6.0'"`), и расхождения версий между таргетами — это норма,
а не находка.

## What Changes

Появляется консольная утилита `tfm-audit` на `net6.0`, которая:

- читает `project.assets.json` (результат restore, то есть факт, а не предположение) и строит граф
  зависимостей отдельно для каждого таргета проекта;
- находит пакеты, чей выбранный ассет относится к более раннему поколению, чем таргет, и разносит
  их по трём уровням: ошибка (отставание на 2+ поколения или ассет чужого семейства),
  предупреждение (1 поколение, `netstandard1.x`, `frameworkAssemblies`), информация
  (`netstandard2.x`, устаревшие только MSBuild-ассеты);
- объясняет каждую находку: путь ассета внутри пакета, насколько он отстаёт, какие прямые
  зависимости его притащили и какими цепочками;
- подсказывает, что часть найденных пакетов вообще входит в состав рантайма и их ссылки можно
  просто убрать;
- строит раздел «Что обновить», честно разделяя находки, достижимые из одного корня, и находки,
  достижимые из нескольких;
- по флагу `--online` спрашивает у NuGet-фида минимальную версию с ассетом под целевой TFM;
- выдаёт результат в шести форматах: консоль, Markdown, самодостаточный HTML с интерактивным
  графом, JSON для CI, Graphviz DOT и DGML.

Правила классификации общие: логика работает на любой паре «таргет — ассет» внутри одного
семейства, включая `net8.0` под `net10.0`, и не захардкожена под net6/net8.

## Capabilities

### New Capabilities
- `assets-graph-analysis`: чтение `project.assets.json`, разбор и сравнение TFM, определение
  выбранных ассетов, построение графа и атрибуция находок до прямых зависимостей
- `outdated-tfm-detection`: классификация ассетов относительно таргета, уровни находок,
  база знаний о пакетах, входящих в состав рантайма, честный расчёт эффекта обновления
- `upgrade-advice`: опциональный опрос NuGet V3 — минимальная версия пакета с ассетом под таргет
- `audit-reporting`: шесть форматов отчёта, включая самодостаточный HTML с послойным
  интерактивным графом
- `audit-cli`: контракт командной строки, разрешение входных путей, коды возврата, справка

### Modified Capabilities
Изменений в существующих спецификациях нет: проект создаётся с нуля.

## Impact

- Новый репозиторий `TfmAudit`: один проект `src/TfmAudit/TfmAudit.csproj`, ноль
  `PackageReference` — только BCL из состава net6
- Никакого влияния на анализируемые проекты: утилита читает `project.assets.json` и ничего не
  изменяет ни в csproj, ни в кеше пакетов
- Внешние зависимости появляются только в режиме `--online`: NuGet V3 API и `NuGet.config`
  пользователя для адресов фидов и учётных данных
- Пригодна для встраивания в сборку: `--fail-on error --quiet --json` даёт ненулевой код возврата
  и машиночитаемый отчёт
