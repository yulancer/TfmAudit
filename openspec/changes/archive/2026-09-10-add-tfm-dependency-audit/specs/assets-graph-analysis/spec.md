## Purpose
Чтение `project.assets.json` и построение по нему графа зависимостей отдельно для каждого таргета
проекта: узлы — разрешённые пакеты и project-ссылки, корни — прямые зависимости из csproj, рёбра —
заявленные зависимости пакетов. На этом графе строится атрибуция: кто притащил конкретный пакет и
каким путём.

## ADDED Requirements

### Requirement: Разбор assets-файла
Анализатор ДОЛЖЕН читать `project.assets.json` формата NuGet версии 3 и извлекать из него секции
`targets`, `libraries`, `projectFileDependencyGroups`, `project.frameworks` и
`project.restore.frameworks`, не полагаясь на присутствие необязательных полей.

#### Scenario: Полный assets-файл мультитаргетного проекта
- **GIVEN** `project.assets.json` проекта с `<TargetFrameworks>net6.0;net8.0</TargetFrameworks>`
- **WHEN** анализатор читает файл
- **THEN** он видит два таргета, их прямые зависимости, project-ссылки и полный список
  разрешённых пакетов с путями выбранных ассетов

#### Scenario: Файл, который не является assets-файлом
- **GIVEN** JSON-файл без секции `targets`
- **WHEN** анализатор пытается его прочитать
- **THEN** он сообщает, что файл не похож на `project.assets.json`, и не роняет процесс

### Requirement: Разбор и сравнение TFM
Анализатор ДОЛЖЕН разбирать короткие имена таргет-фреймворков (`net8.0`, `net8.0-windows7.0`,
`netcoreapp3.1`, `netstandard2.0`, `net48`), относить их к семейству и сравнивать версии только
внутри одного семейства.

#### Scenario: net5+ и netcoreapp — одно семейство
- **GIVEN** TFM `net8.0` и `netcoreapp3.1`
- **WHEN** анализатор их разбирает
- **THEN** оба относятся к семейству .NET Core / .NET 5+, и `netcoreapp3.1` признаётся отстающим
  от `net8.0` на пять мажорных поколений

#### Scenario: Точечная запись до пятой версии — это .NET Framework
- **GIVEN** TFM `net4.8`
- **WHEN** анализатор его разбирает
- **THEN** он относится к семейству .NET Framework, а не к .NET Core

#### Scenario: Неизвестный монитор не ломает анализ
- **GIVEN** TFM вида `tizen40` или пустая строка
- **WHEN** анализатор его разбирает
- **THEN** возвращается значение с неизвестным семейством, исключение не выбрасывается

### Requirement: Определение выбранных ассетов
Анализатор ДОЛЖЕН определять TFM ассетов, которые restore фактически выбрал для таргета, разбирая
пути из секций `compile`, `runtime`, `runtimeTargets`, `embed`, `build`, `buildTransitive`,
`buildMultiTargeting`, `contentFiles` и `tools`.

#### Scenario: Ассеты кода приоритетнее MSBuild-ассетов
- **GIVEN** пакет, у которого `compile` указывает на `lib/net8.0/`, а `build` — на `build/net6.0/`
- **WHEN** анализатор определяет худший ассет
- **THEN** решение принимается по ассетам кода, а устаревание MSBuild-ассетов учитывается
  как ослабляющее обстоятельство, а не как основная находка

#### Scenario: Пустая заглушка не считается ассетом
- **GIVEN** пакет с путём `lib/net6.0/_._` под таргетом `net8.0`
- **WHEN** анализатор разбирает его ассеты
- **THEN** путь распознаётся как заглушка «совместим, но ассетов нет» и не порождает находку

#### Scenario: Аналайзеры не привязаны к таргету
- **GIVEN** пакет, у которого есть только `analyzers/dotnet/cs/*.dll`
- **WHEN** анализатор определяет TFM ассетов
- **THEN** пакет помечается как не имеющий TFM-зависимых ассетов и не попадает в находки

### Requirement: Определение корней графа
Анализатор ДОЛЖЕН считать корнями графа прямые `PackageReference` таргета,
прямые `ProjectReference` из `project.restore.frameworks`, а также любые узлы,
на которые не ссылается ни один другой узел.

#### Scenario: Project-ссылка — такой же корень, как пакет
- **GIVEN** проект, у которого часть зависимостей приходит через `ProjectReference`
- **WHEN** анализатор строит граф
- **THEN** эти проекты попадают в число прямых зависимостей и объясняют происхождение пакетов,
  достижимых только через них

#### Scenario: Ни один пакет не остаётся без объяснения
- **GIVEN** граф, в котором есть пакет, недостижимый из объявленных прямых зависимостей
- **WHEN** анализатор строит граф
- **THEN** такой пакет получает корень за счёт правила «нулевая входящая степень», и его глубина
  не остаётся нулевой

### Requirement: Нормализация идентификаторов пакетов
Анализатор ДОЛЖЕН приводить имена зависимостей к каноническому регистру пакета из секции
`targets`, поскольку в assets-файле они записаны в регистре nuspec ссылающегося пакета.

#### Scenario: Регистр из nuspec не попадает в отчёт
- **GIVEN** пакет, объявивший зависимость как `microsoft.data.sqlclient`, при каноническом
  идентификаторе `Microsoft.Data.SqlClient`
- **WHEN** анализатор выводит цепочку зависимостей
- **THEN** в цепочке используется канонический идентификатор

### Requirement: Атрибуция находок и цепочки зависимостей
Анализатор ДОЛЖЕН для каждой находки определять полный набор прямых зависимостей, из которых она
достижима, и строить кратчайшие цепочки от этих зависимостей до проблемного пакета.

#### Scenario: Пакет достижим из нескольких прямых зависимостей
- **GIVEN** пакет, достижимый и из `A`, и из `B` — двух прямых зависимостей проекта
- **WHEN** анализатор формирует находку
- **THEN** в ней перечислены обе прямые зависимости и показаны цепочки от каждой из них,
  начиная с самой короткой

#### Scenario: Ограничение числа цепочек
- **GIVEN** находка, достижимая из десяти прямых зависимостей, и настройка «не более трёх цепочек»
- **WHEN** анализатор формирует находку
- **THEN** показываются три самые короткие цепочки, а полный список виновников сохраняется целиком

### Requirement: Независимость таргетов друг от друга
Анализатор ДОЛЖЕН анализировать каждый таргет относительно его собственного TFM и НЕ ДОЛЖЕН
сообщать о расхождениях версий между таргетами одного проекта.

#### Scenario: Условная ссылка на разные версии не является находкой
- **GIVEN** csproj, где под `net6.0` подключён `Microsoft.Extensions.Hosting.Abstractions 6.0.0`,
  а под `net8.0` — версия `8.0.1`
- **WHEN** анализатор обрабатывает оба таргета
- **THEN** под каждым таргетом оценивается только его собственный ассет, а сам факт расхождения
  версий между таргетами находкой не считается
