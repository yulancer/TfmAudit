## Context

Единственный надёжный источник данных о том, какие ассеты реально попали в сборку, —
`project.assets.json`. Это результат восстановления: в секции `targets/<tfm>` NuGet уже записал
**выбранные** пути (`compile`, `runtime`, `runtimeTargets`, `build`, …). Значит анализатору не надо
повторять правила совместимости TFM — достаточно прочитать факт и сравнить TFM выбранной папки с
таргетом.

Ограничения, заданные заказчиком: утилита под `net6.0`, консольная. Из этого следует отказ от
пакетов `NuGet.*` (они тянут за собой десятки транзитивных ссылок и сами страдают той же болезнью,
которую мы диагностируем) — семантика версий и разбор TFM реализуются явно.

Проверочный пример — реальный `project.assets.json` сервиса на 231 узел с мультитаргетом
`net6.0` + `net8.0`, включённым `AssetTargetFallback` на net461…net481, семью `ProjectReference`
и внутренними пакетами `Contoso.Platform.*` / `Contoso.Core.*`.

## Goals / Non-Goals

**Goals:**
- Ответить на вопрос «что обновить в csproj», а не просто перечислить старые пакеты
- Сделать вывод проверяемым руками: путь ассета внутри пакета, цепочка зависимостей
- Работать полностью офлайн; сеть — только опциональное обогащение
- Не давать ложных срабатываний на мультитаргетности и условных ссылках
- Правила, общие для любых TFM, включая будущие поколения

**Non-Goals:**
- Не править csproj и не выполнять обновления — только анализ и объяснение
- Не заменять `dotnet list package --outdated`: тот отвечает «есть ли версия новее»,
  а мы — «какой ассет реально выбран и кто его притащил»
- Не анализировать IL и фактическое использование API
- Не поддерживать NuGet V2 и локальные папки-источники

## Decisions

**Читать `project.assets.json`, а не csproj.** csproj говорит о желаемом, assets — о случившемся.
Транзитивные зависимости в csproj вообще не видны, а именно они и составляют проблему.

**Анализировать каждый таргет независимо.** Прямое следствие требования «мультитаргетность не
ошибка». Побочный плюс: под таргетом `net6.0` net6-ассеты корректно считаются нормой, и один и тот
же файл даёт разные картины по таргетам — это и нужно оператору при поэтапном переходе.

**Уровень находки задавать разрывом в мажорных поколениях, а не списком «плохих» TFM.**
Разрыв ≥ 2 — ошибка, разрыв 1 — предупреждение. Так правило автоматически работает для `net8.0`
под `net10.0` и не требует правок при выходе новых версий.

**`netstandard2.x` — информация, а не ошибка.** Он совместим с любым современным .NET. Если бы это
была ошибка, отчёт по реальному проекту утонул бы в шуме: в примере таких пакетов 48 из 224.
Уровень при этом можно повысить флагом для тех, кто хочет вычистить и его.

**Корнями графа считать не только `PackageReference`.** `ProjectReference` — такая же прямая
зависимость, а в примере семь пакетов достижимы только через них. Плюс страховка: узлы с нулевой
входящей степенью тоже становятся корнями, иначе часть пакетов осталась бы без объяснения
«кто их притащил» (в первой версии так и вышло с `Confluent.Kafka`).

**Идентификаторы приводить к каноническому регистру.** В assets ключи зависимостей записаны в
регистре nuspec ссылающегося пакета, поэтому в цепочках всплывало `microsoft.data.sqlclient`.
Граф строится на нормализованных рёбрах.

**Отказаться от жадного покрытия в разделе «Что обновить».** Первая версия выдавала «минимальный
набор прямых зависимостей, который закрывает все находки». Это неправда: если находка достижима
из двух корней, обновление одного её не убирает — второй продолжает тянуть свою копию. Вместо
покрытия считается влияние: число находок, достижимых ровно из одного корня (гарантированный
выигрыш), и число достижимых из нескольких (нужно обновить всех виновников). Сортировка — по
числу эксклюзивных находок.

**Поиск версии в фиде — бинарный.** Поддержка TFM монотонна по версиям пакета, поэтому вместо
перебора N версий достаточно порядка 2·log₂(N) запросов: сначала по представителям минорных
линеек, затем внутри найденной линейки. На пакете с сотней версий это 12–14 запросов вместо ста.

**Поддержкой таргета считать наличие папки ровно под целевой TFM.** Папка `net9.0` при таргете
`net8.0` находку не снимает: restore выберет ближайшую не превышающую, то есть по-прежнему старую.

**HTML-отчёт — один файл без внешних ресурсов.** Отчёт пересылают в мессенджере и открывают на
машинах без интернета; CDN и веб-шрифты это ломают. Шаблон лежит в ресурсах сборки, данные
подставляются как JSON в `<script type="application/json">` с экранированием угловых скобок.

**Граф раскладывать по слоям, а не силовым алгоритмом.** Слои = глубина от проекта, порядок внутри
слоя — медианная эвристика для уменьшения пересечений. Силовая раскладка на 230 узлах даёт клубок,
а слои прямо отвечают на вопрос «на каком уровне сидит проблема». По умолчанию показываются только
пути до ошибок: полный граф нечитаем даже послойно.

## Risks / Trade-offs

**Определение TFM по `.nuspec` неточно** → у пакета группы зависимостей могут не совпадать с
папками `lib/`. Смягчение: флаг `--deep` читает папки прямо из `.nupkg`, а способ определения
попадает в отчёт, чтобы оператор видел, насколько доверять совету.

**База знаний о пакетах, входящих в рантайм, устаревает** → подсказки формулируются как гипотезы
(«как правило, не нужна», «попробуйте убрать»), а не как указания, и всегда сопровождаются
проверяемым фактом: путём ассета и цепочкой.

**`netstandard2.x` на уровне «информация» может скрыть реальную проблему** → распределение по TFM
выводится гистограммой целиком, так что масштаб виден даже при фильтрации находок.

**Отсутствие автотестов** → проверка держится на прогоне по реальному примеру и рендере HTML в
headless-браузере. Для утилиты такого размера это осознанный компромисс, но любое изменение правил
классификации требует сверки гистограммы на примере.

**Ручная реализация семантики версий NuGet** → покрыт разбор четырёх числовых компонентов,
pre-release по semver и build-метаданных; экзотические записи могут отсортироваться иначе, чем в
NuGet. Цена ошибки невелика: пострадает только совет по версии, а не сам анализ.

## Migration Plan

Миграции нет: новый инструмент, ничего не заменяет и не изменяет анализируемые проекты.
Внедрение — запуск на одном сервисе, затем `--fail-on error` в сборке после того, как текущий
слой находок разобран.

## Open Questions

- Стоит ли считать `netstandard2.x` предупреждением по умолчанию, когда основной слой net6 будет
  вычищен? Сейчас это флаг, решение можно поменять по опыту эксплуатации.
- Нужен ли режим сравнения двух прогонов («что изменилось после обновления»)? Пока эту роль
  выполняет повторный запуск и глазомер.
